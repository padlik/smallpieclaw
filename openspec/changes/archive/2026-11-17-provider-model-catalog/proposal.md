## Why

Model choices and limits are tied to static or operator-maintained entries, making provider inventories stale and selection, context budgeting, and execution defaults unreliable. A provider-backed catalog with explicit persisted selection will make model knowledge consistent while remaining safe when metadata or service access is unavailable.

## What Changes

- Add provider connections `[providers.<provider-id>]` with `type`, `api_key`, `base_url`, and `request_timeout`; `type` selects `openai`, `openrouter`, `anthropic`, `google`, or cloud-only `ollama`. Discover model IDs and reliable capabilities/limits through each provider's supported catalog API. The connection ID and exact upstream model ID (split at the first `/`) identify a model; catalog availability does not promise account callability.
- Add app-owned `$XDG_CONFIG_HOME/<agent>/models-config.toml` for discovered catalogs and remembered main-model ID. Refresh at startup and `/models`; replace inventory only after a successful per-provider refresh, retain and visibly mark last-good stale inventory on failure, and never silently replace a saved ID. If the saved ID is absent from inventory, retain it and gate model work; if no ID is saved, likewise keep daemon/commands running but gate model work until explicit `/models` selection. Persist each deliberate selection and report persistence failure honestly. Offer a simple roughly-20-item listing; handle Telegram callback limits without a general pagination system, and select only discovered entries. Prompt/tool model consumers share this registry to show available and active models plus known/unknown/stale capabilities, never secrets; availability does not promise account callability.
- Resolve explicit run model selections at admission, otherwise snapshot the active main model; pin its model, endpoint, and metadata through that run. There is no automatic model fallback, including for vision and on-demand, plan, and diagnostic runs, whose selectors stay strict; every ordinary admission requires an active main model, even for an explicit known canonical selector. The one settled exception is scheduled jobs: scheduler jobs and their configuration never decide whether the bot starts, and job errors are contained to that job. A missing or `None` saved job model is a silent inherit marker on job add, load, and execution: it is not malformed and produces no warning. At execution, a malformed saved job selector (an empty or whitespace-only string, or any non-`None` non-string value) or an exact non-blank string that cannot be resolved in the catalog (absent entry) warns and inherits the active main model, provided the main model itself is valid; exact non-blank strings are preserved without trimming, as is every raw saved selector, and none is silently normalized, dropped, stringified, or rewritten, and the main selection stays unchanged. Stale discovered entries remain resolvable and selectable; provider staleness is not an unknown selector. With no catalog there is no valid main model, so the job fails normally. If no valid active main model exists, any scheduled job fails normally before any model call, including one with a valid explicit canonical selector; the ordinary admission gate is unchanged. This selector-resolution fallback applies only before admission; a valid explicit job selector that later hits a credential, capability, context, inference, or provider-outage error never falls back and never triggers a cross-model retry. Job add with an omitted or `None` model inherits; modify with an omitted or `None` model leaves it unchanged (no clear operation). Job run-ID/active tracking and `last_run` history are still recorded before spawn and the terminal record after, with no pre-spawn terminal row or trace invented. No job converter or job rewrite is included; parsing, persistence, and invalid-representation details are reserved for design. Remove startup-frozen `agent.background_model`.
- Use known model context metadata when present; if absent, use `agent.ctx_max_tokens` as a visible **assumed local budget**, not a claim about provider capacity. Omit `temperature`/`top_p` from ordinary chat, native-tool, and JSON requests; omit an output cap when optional. If required, derive it from reliable model-specific output metadata bounded by remaining context; unknown required output limits fail actionably. Unknown vision capability is visible and image requests fail safely; `vision_query` requires an explicitly selected verified vision model. A manual switch to a smaller model stays selected, but an oversized next request fails without truncating history/source; ordinary compaction remains.
- Require explicit valid canonical `graph_memory.extraction_model` and global `[embeddings]` model/provider when graph memory is enabled; otherwise warn actionably at startup and disable graph only, while standalone live backfill fails before any database side effect and dry-run touches no database, embedding, or inference. Graph extraction and live backfill resolve the configured canonical extraction selector independently of main selection through a proposed registry resolution (`resolve_graph_model(selector: str) -> RunModel`, not an existing API) that leaves main selection, settings, and revisions unchanged; ordinary admission still requires an active main model. One settled pin per graph component or backfill invocation; extraction clients keep owned construction. Graph prerequisite budgeting follows the existing request-budget rules: an unknown output limit is allowed even with the fixed 1024 cap, unknown context uses the labelled local fallback, and a known output limit below 1024, malformed limits, or non-positive headroom fail. Google resource names and supported generation methods are discovery-only and never imply capabilities. Embeddings remain independent of chat selection and chat credentials/endpoints; preserve explicit embedding configuration and matching-provider inheritance, but remove fallback to active-chat credentials. Preserve graph extraction's fixed `temperature=0.1` and `max_tokens=1024` as a named exception to ordinary request parameter rules.
- Set `[agent] max_retries=4` (additional attempts, five total), `retry_delay=2.0s`, exponential delays 2/4/8/16; `max_retries=0` means the initial attempt only. Remove provider/model retry knobs. Retry transient provider failures only; permanent failures stop immediately. Keep one automatic attempt budget across native/JSON, human-wait, and empty-output control-flow paths. Retry a failed current request only before it emitted output or caused a side effect; earlier completed tool turns need not prevent retry of a later failed request. Never replay completed tools or a whole run automatically. Explicit checkpoint recovery remains user-directed, not an automatic retry or implicit budget reset; terminal errors end the run, not the bot.
- **BREAKING:** Replace `[[models]]`/per-model settings with provider connections and discovered catalogs; remove per-model/provider generation and retry tuning, moving retry controls to `[agent]`, and remove per-call generation overrides (including `max_tokens`, `temperature`, and `top_p`). Move main selection from `agent.default_model` to app-owned preferences; remove `agent.background_model`. Remove/reject explicit agent-level fallback settings in human configuration; a legacy per-job `fallback_models` setting is instead ignored with a runtime warning when that job executes, never as a job-load or startup error, and the job configuration is left unrewritten (it never enables cross-model retry). Remove vision auto-routing, and local Ollama defaults/selection (local Ollama users must explicitly choose a cloud replacement; do not guess from `:cloud`). Migrate only unambiguous configuration using preview, backup, recovery, and idempotent reruns; preserve unresolved TOML references without expanding secrets, report discarded tuning without promoting it or creating hidden overrides, require operator choice for ambiguous account selectors, and seed the main selection only from an unambiguous old startup default. Do not rewrite jobs, logs, prompts, memories, vectors, or reconstruct manual-switch history.

## Capabilities

### New Capabilities
- `provider-model-catalog`: Provider connections, discovered catalog and metadata, persistence/refresh, explicit selection, admission-time run model resolution/pinning, the scheduled-job selector exception, independent graph model resolution, migration, graph prerequisites, and shared availability reporting.

### Modified Capabilities
- `per-model-context-window`: Use catalog context/output metadata, expose unknown context limits while retaining the assumed local budget, remove vision auto-routing and fallback selectors, and preserve normal compaction.
- `provider-credential-inheritance`: Replace configured model entries; preserve explicit embedding configuration and provider inheritance, but prohibit active-chat credential fallback for embeddings.
- `llm-error-recovery`: Define bounded agent retry defaults while keeping explicit checkpoint recovery distinct and preserving terminal bot behavior.
- `agent-runtime-construction`: Remove per-call generation-tuning overrides and carry the admission-resolved model contract through runtime construction.
- `native-tool-calling`: Use the shared request parameter contract and retry budget across native/JSON requests without resetting the budget or replaying completed tool effects.
- `xdg-path-resolution`: Resolve the app-owned model-catalog file beneath the agent's XDG config directory.
- `scheduled-job-execution`: Add execution-time model selection for scheduled jobs: startup independence from job configuration, contained per-job errors, inherit-main handling of malformed or unknown selectors, and unchanged run-ID/history ordering.
- `telegram-command-surface`: Add `/models` for catalog listing, refresh, and explicit main-model selection.

## Impact

Configuration and provider adapters (`config_schema.py`, `main.py`, `llm_client.py`, `providers/`); catalog persistence and XDG paths (`xdg.py`); request budgeting (`react_loop.py`, `context_manager.py`); graph startup/backfill (`graph_memory.py`, `backfill_graph_memory.py`); run admission (`agent_runtime.py`, `agent_controller.py`, `scheduler.py`, `builtin_tools/schedule.py`); prompt/tool model awareness (`prompt_builder.py`, `prompt_loader.py`, built-in tool schemas/descriptors); Telegram interface, commands, callbacks, and help; migration and config examples. Existing provider API dependencies remain; no dependency is required.
