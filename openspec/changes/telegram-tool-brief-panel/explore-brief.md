# Explore Brief — telegram-tool-brief-panel

## Problem

During agent execution, the Telegram progress panel shows tool calls as two separate lines per tool (TOOL_START then TOOL_END), with the tool name only — arguments are generated by `fmt_tool_call` (react_loop.py:364-381) but stripped by `_ProgressPanel.classify()` (telegram_interface.py:165-169). The user sees `Running: shell` with no indication of *what* command is running. With 10 visible steps and 2 lines per tool call, the panel shows ~5 tool calls and feels noisy.

## Rejected alternatives

- **Option A (stop stripping args in classify)** — cheapest, but inherits `fmt_tool_call`'s format (`shell $ cmd`, `file_read read: path`) which doesn't match the desired style, and leaves most tools on ugly generic JSON.
- **Option C (reuse confirmation descriptions, truncated)** — conceptually elegant (single source of truth), but confirmation descriptions are multi-line HTML-formatted strings built for a different context; one-lining them is fiddly and not all tools have a confirmation desc.
- **Option D (dedicated `__TOOL_BRIEF__` progress prefix)** — clean separation, but over-engineered for a one-line display improvement; adds another magic-string protocol to maintain.

## Selected approach — Option B: purpose-built brief formatter

New `fmt_tool_brief(tool_name, args, is_mcp=False, server_name="")` function in `react_loop.py` with per-tool branches and a generic fallback. The brief is emitted in the existing "Running tool:" progress string (react_loop.py:1393). `_ProgressPanel.classify()` is modified to keep the brief instead of stripping it. TOOL_END updates the last step in place (merging ✅/❌ onto the Running line), reusing the `__SHELL_CHUNK__` in-place update pattern (telegram_interface.py:289-304).

### Shell wrapper stripping (Layer 1)

Strip these patterns in order, then truncate to ~35 chars with `…`:
1. `^(sh|bash|zsh)\s+-c\s+"(.+)"$` → inner command
2. `^cd\s+\S+\s+&&\s+` → everything after `&&`
3. `^export\s+\w+=\S+\s+&&\s+` → everything after `&&`

### Secrets handling

- `secret_get`: show key only, never value (mirrors confirmation builder at secrets_log.py:55)
- `shell_env_set`: show key only, never value (value may be a secret token)
- `shell` command: truncation at ~35 chars is the pragmatic shield; secrets in the first 35 chars are visible, same exposure as the confirmation prompt
- `file_write`/`file_patch`: never show content/old_str/new_str — only basename + size/line counts

### Path display

Basename only (not last-2-components). Simpler, sufficient for this stage.

### file_write size unit

`len(content)` (chars) — simplest, minimum effort. Display as `(340)` with no unit suffix.

## Cross-module data flow

```
react_loop.py:1393 (TOOL_START)
   │  tool_name, args from action_obj
   │  is_mcp, server_name looked up via ctx.mcp_manager / ToolRegistry
   │
   │  emits:  f"{icon} Running tool: `{name}`\n{brief}"
   │          where brief = fmt_tool_brief(name, args, is_mcp, server_name)
   │
   ▼
progress_callback (string channel)
   │
   ▼
_ProgressPanel.dispatch_progress(msg)   [telegram_interface.py:230]
   │
   ├─ "Running tool:" msg
   │   └─ classify() parses name + brief, renders one HTML line
   │      appends to _steps with tag=TOOL_RUNNING
   │
   ├─ "__SHELL_CHUNK__:" msg
   │   └─ updates last step in place (existing behavior, preserved)
   │
   ├─ TOOL_END msg ("**shell** ✅" or "❌")
   │   └─ NEW: updates last step in place, appends ✅/❌
   │      (instead of appending a new step)
   │
   └─ "Thinking…" msg
       └─ appends with tag=THINKING
       └─ when next step arrives and last was THINKING,
          retroactively patches duration onto it
```

### MCP server name lookup

At react_loop.py:1393, before emitting the progress string:
- `ctx.mcp_manager.has_tool(tool_name)` → if True, look up `Tool` via `ToolRegistry.get(tool_name)` to get `server_name`
- Pass `is_mcp=True, server_name=tool.server_name` into `fmt_tool_brief()`
- The brief appends ` [MCP:{server_name}]` for MCP tools

## Panel changes

- `_MAX_STEPS`: 10 → 5 (one line per tool call shows the same density as 10 two-line steps)
- `_steps` tuple: `(elapsed, html)` → `(elapsed, html, tag)` where tag ∈ {None, "TOOL_RUNNING", "THINKING"}
- `build_panel()`: unchanged rendering, just fewer visible steps
- Thinking duration: retroactive patch when the next step arrives (not a live timer)

## What stays unchanged

- `fmt_tool_call()` — still used by verbose mode and the full result line
- `fmt_tool_result_progress()` — the TOOL_END result line with output tail (verbose only)
- Confirmation flow — unchanged, still shows full descriptions
- `/verbose` mode — unchanged, still sends full args as separate messages
- `LogEvent` taxonomy — unchanged, still structlog-only (not wired to Telegram)
- `on_tool_trace` hook — unchanged, still unwired for main agent

## Open questions

1. **Thinking duration display**: retroactive patch (duration appears when next step arrives) vs live-ticking timer. Decision: retroactive patch — simpler, no timer thread.
2. **`__SHELL_CHUNK__` interaction with merged line**: shell tail shows while running, dropped on TOOL_END (replaced by ✅/❌). Decision: drop tail on TOOL_END to keep one line.
3. **MCP tools with no args**: brief would be just `[MCP:server_name]`. Acceptable — still tells the user which MCP server is active.
4. **Unknown tool names** (not in BUILTIN_TOOLS, not MCP): generic fallback `<name> <compact_args_repr>`. No `[MCP]` marker.
