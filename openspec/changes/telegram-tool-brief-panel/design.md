## Context

The Telegram progress panel (`_ProgressPanel` in `telegram_interface.py:106-308`) is the operator's live view of agent execution. It renders a scrolling log of the last 10 steps, each step being one line. Today, every tool call produces two steps: a TOOL_START line (`Running: shell`) and a TOOL_END line (`shell ✅`). The tool arguments are generated by `fmt_tool_call()` (`react_loop.py:364-381`) and included in the progress string, but `_ProgressPanel.classify()` (`telegram_interface.py:165-169`) strips everything after the tool name — so the user sees only the tool name, never the arguments.

The panel already has a precedent for in-place step updates: the `__SHELL_CHUNK__` handler (`telegram_interface.py:289-304`) updates the last step in place to show a live shell-output tail. This change extends that pattern to merge TOOL_END into the TOOL_START step, adds a per-tool brief formatter, and reduces visible steps from 10 to 5.

## Goals / Non-Goals

**Goals:**
- Show a short per-tool brief (~35 chars) on the Running line so the operator knows *what* the tool is doing, not just *that* a tool is running.
- Merge TOOL_START and TOOL_END into a single panel line (✅/❌ appended to the Running line) to halve visual noise.
- Mark MCP tools with `[MCP:server_name]` so the operator can distinguish built-in vs external tool calls.
- Show `Thinking… Ns` duration so the operator knows how long the LLM is taking between tool calls.
- Reduce visible steps from 10 to 5 (same information density with merged lines).
- Strip shell wrapper noise (`sh -c`, `cd X &&`, `export VAR=… &&`) so the brief shows the actual work.

**Non-Goals:**
- Live-ticking Thinking timer (retroactive patch only — duration appears when the next step arrives).
- Per-tool briefs for MCP tools (generic fallback with `[MCP:server]` marker only).
- Changing verbose mode, confirmation flow, `fmt_tool_call()`, `fmt_tool_result_progress()`, `LogEvent` taxonomy, or `on_tool_trace` hook.
- Changing `build_panel()` rendering logic (only `_MAX_STEPS` and the `_steps` tuple shape change).
- Secrets redaction beyond truncation (shell commands may show secrets in the first 35 chars — same exposure as the confirmation prompt).

## Decisions

### Decision 1: New `fmt_tool_brief()` function in `react_loop.py`

**Choice:** Add a new `fmt_tool_brief(tool_name, args, is_mcp=False, server_name="")` function alongside the existing `fmt_tool_call()`.

**Rationale:** `fmt_tool_call()` produces multi-line markdown-formatted output designed for verbose mode and the result line. The brief needs a single-line, HTML-escapable string for the compact panel. Reusing `fmt_tool_call()` would require stripping markdown fences and truncating — fiddly and fragile. A separate function keeps the two concerns cleanly separated.

**Alternatives considered:**
- *Reuse `fmt_tool_call()` and strip in `classify()`* — rejected because `fmt_tool_call()` wraps in triple-backtick fences and uses `$ cmd` / `read: path` formats that don't match the desired brief style.
- *Reuse confirmation `description` builders* — rejected because they produce multi-line HTML strings built for a different context (approval prompt), and not all tools have one.

### Decision 2: Per-tool brief extraction logic

**Choice:** Each built-in tool gets a branch in `fmt_tool_brief()` that extracts the semantically meaningful argument:

| Family | Extraction | Example |
|---|---|---|
| Path-based (file_read, file_send, vision_query) | `os.path.basename(path)` | `config.yaml` |
| `file_diff` | `basename_a ↔ basename_b` | `a.py ↔ b.py` |
| `file_patch` | basename + derived `+N -M` line counts | `app.py +12 -3` |
| `file_write` | basename + `len(content)` | `app.py (340)` |
| Shell | wrapper-stripped command, truncated ~35 chars | `python3 -c "import json…` |
| Task-based (spawn_agent, schedule) | `task` / `action + tag` | `"research React 19…` |
| Key-based (secret_get, shell_env_set/unset/get) | `key` (never value) | `API_KEY` |
| `memory_write` | `action` + `"key"` | `set "user_prefs"` |
| `memory_graph_search` | `"query"` | `"user entities"` |
| `memory_graph_store` | `"content"` (~30 chars) | `"Meeting notes:…` |
| `log_query` | `"text"` or filter | `"TOOL_FAILED"` |
| ID-based (get_agent_result, cancel_agent) | `agent_id` | `sa-abc123` |
| `wait_for_any_agent` | `[N agents]` if >2, else list | `[3 agents]` |
| `shell_env_list` | static string | `list env vars` |

**Rationale:** The primary argument is the one that tells the operator what's happening. Derived counts (`+N -M` for file_patch, `(N)` for file_write) add signal without showing raw content. Secrets are protected by showing keys only, never values.

### Decision 3: Shell wrapper stripping (Layer 1)

**Choice:** Strip three wrapper patterns in order before truncating:
1. `^(sh|bash|zsh)\s+-c\s+"(.+)"$` → inner command
2. `^cd\s+\S+\s+&&\s+` → everything after `&&`
3. `^export\s+\w+=\S+\s+&&\s+` → everything after `&&`

Then truncate to ~35 chars with `…`.

**Rationale:** These wrappers are agent-generated plumbing, not the operator's work. Stripping them reveals the actual command. Layer 1 is cheap and high-signal; deeper parsing (extracting program + first arg) is fragile and rejected.

### Decision 4: Merge TOOL_END into TOOL_START step (in-place update)

**Choice:** When a TOOL_END progress message arrives, update the last step in place (append ✅/❌) instead of appending a new step. This reuses the `__SHELL_CHUNK__` in-place update pattern (`telegram_interface.py:289-304`).

**Rationale:** Halves visual noise (one line per tool call instead of two). The `__SHELL_CHUNK__` handler already proves this pattern works. The step's elapsed timestamp stays at the TOOL_START time.

**Edge case — intervening Thinking step:** If a Thinking step was appended between TOOL_START and TOOL_END (shouldn't happen in normal flow — TOOL_END follows TOOL_START directly), the merge finds the last TOOL_RUNNING step by tag and updates it, skipping any intervening Thinking steps.

### Decision 5: `_steps` tuple gains a `tag` field

**Choice:** Change `_steps: list[tuple[float, str]]` to `_steps: list[tuple[float, str, str | None]]` where the third element is a tag: `"TOOL_RUNNING"`, `"THINKING"`, or `None`.

**Rationale:** The merge logic needs to distinguish "is the last step a tool call I should update?" from "is it a Thinking step?". Parsing HTML to determine this is fragile. A lightweight tag makes the logic explicit and enables the Thinking-duration retroactive patch.

### Decision 6: Thinking duration via retroactive patch

**Choice:** When a new step arrives and the last step has tag `THINKING`, compute the duration between the Thinking step's elapsed time and the new step's elapsed time, then patch the Thinking step's HTML to include ` Ns`.

**Rationale:** A live-ticking timer would require a background asyncio task editing the panel every second — complex and throttled. The retroactive patch is a single in-place update when the next step arrives, reusing the same update pattern as TOOL_END merge. The user briefly sees `Thinking…` without a duration, then it gets patched — acceptable trade-off for simplicity.

### Decision 7: MCP marking via `ToolRegistry.get()` lookup

**Choice:** At `react_loop.py:1393`, before emitting the TOOL_START progress string, check `ctx.mcp_manager.has_tool(tool_name)`. If True, look up `ToolRegistry.get(tool_name)` to get `server_name`, and pass `is_mcp=True, server_name=tool.server_name` to `fmt_tool_brief()`. The brief appends ` [MCP:{server_name}]`.

**Rationale:** `Tool.server_name` is already populated by `mcp_client.py` at registration time (`tool_registry.py:53-62`). No new infrastructure needed — just a read-only lookup at the emission site.

### Decision 8: `_MAX_STEPS` 10 → 5

**Choice:** Reduce the visible step count from 10 to 5.

**Rationale:** With merged lines (one per tool call), 5 steps show ~5 tool calls — the same information density as the current 10 steps showing ~5 tool calls × 2 lines each. The panel stays compact on mobile screens.

### Decision 9: `__SHELL_CHUNK__` preserves brief, drops tail on TOOL_END

**Choice:** While a shell command is running, `__SHELL_CHUNK__` updates the last step to show the brief + live tail. When TOOL_END arrives, the tail is dropped and replaced by ✅/❌, keeping the line clean.

**Rationale:** The tail is a live preview useful while the command runs. Once it finishes, the ✅/❌ is the final state. Showing both would make the line too long. Verbose mode still gets the full output separately.

## Risks / Trade-offs

- **[Shell secrets in brief]** → Truncation at ~35 chars is a partial shield. Mitigation: same exposure as the confirmation prompt which shows the full command; verbose mode is opt-in for full detail.
- **[MCP server-name lookup adds a call per tool]** → `ToolRegistry.get()` is a dict lookup, negligible cost. Mitigation: none needed.
- **[Retroactive Thinking duration is not live]** → User sees `Thinking…` then `Thinking… 5s` a moment later. Mitigation: acceptable for a progress panel; a live timer would add complexity for marginal gain.
- **[TOOL_END without matching TOOL_START]** → If a tool call is interrupted or the progress string is lost, the merge finds no TOOL_RUNNING step. Mitigation: fall back to appending a new step (current behavior).
- **[Brief format changes over time]** → Per-tool branches in `fmt_tool_brief()` need maintenance when new tools are added. Mitigation: generic fallback handles unknown tools; new tools get a branch only if the generic fallback is insufficient.

## Migration Plan

This is a UI-only change with no data migration, no config changes, and no breaking changes to external APIs. Deployment is a single code update. Rollback is reverting the code — no state to restore.

**Verification:** Manual testing via Telegram (run an agent, observe the panel). Automated tests for `fmt_tool_brief()` per-tool branches and `classify()` brief-keeping behavior.

- **ADR-0006** (source-categories-for-agent-visibility) — defines the `on_tool_trace` hook and sub-agent visibility categories. This design leaves `on_tool_trace` unwired for the main agent (sub-agent registry use only). Honored.
- **ADR-0009** (native-tool-calling) — defines how tool calls surface from the ReAct loop. This design modifies only the progress-string content at the emission site (`react_loop.py:1393`), not the tool-calling mechanism itself. Honored.

No in-force ADRs need supersession.
