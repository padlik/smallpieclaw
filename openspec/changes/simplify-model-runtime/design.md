### Component view (one application process; lightweight C4-inspired)

```text
 Operator /models -> discovery -> disposable catalog cache (XDG cache)
          /models -> selection <-> durable preference (XDG config)
 Main + Scheduler -> direct selector resolver -> immutable pinned chat client -> Chat API
 ReAct context statistics -> compactor -> same pinned chat client -> Chat API
 Graph worker + backfill -> independent extraction client -> Graph API
 Indexing + graph vectors -> explicit shared embedding client -> Embedding API
```

These are components, **not** separate deployable services or a new DI container. `main.py` wires the existing interfaces, `AgentRuntime` still builds sub-agent products, scheduler owns job attempts, and graph writer/backfill own extraction lifetimes. Assumption for this proposed design: the existing provider adapters continue to accept configured upstream model identifiers without discovery membership. Any adapter-specific wire restrictions remain real and must be tested, not inferred from cache metadata.

## Goals / Non-Goals

**Goals:** Make discovery advisory and startup deterministic, allow ordinary/scheduled explicit selectors without Main or catalog, pin one connection/upstream per run, give graph and embeddings wholly explicit independent configuration, retain diagnostic token counts and safe successful-summary compaction, remove only obsolete model/scheduler compatibility, and preserve error, security, persistence, and ownership contracts.

**Non-Goals:** Live connection reload, catalog whitelisting or public supplementation/provenance, new model capabilities or vision auto-routing, model switches/fallback/fit tickets, budget/reserve/headroom/overflow repair, per-call generation knobs, new summarization framework, a fourth vector config, broad scheduler rewrite, `/stop`/permissions redesign, XDG migration or historical log/record/memory-format changes. No new dependency or external service.

## Decisions

### 1. Restart-fixed chat connections; disposable discovery and deliberate selection

Parse `[providers.<id>]` once at startup and hold a fixed immutable connection map until restart. Discovery uses only those routes; refresh changes **only** the candidate cache (including ordinary partial provider failures), never the routes, Main preference, admitted clients, or runs. There are no generation/fingerprint/revision checks for live replacement. Cache records need canonical ID and display-only discovery data; do not persist public supplement/provenance or turn capability flags into vision/tool gates. Provider adapter/protocol validation and genuine provider errors still apply.

Use `xdg.py` to resolve two different leaves: durable `$XDG_CONFIG_HOME/<name>/model-selection.toml` containing one deliberate `model = "connection/upstream"` selection, and disposable `$XDG_CACHE_HOME/<name>/models-cache.json` containing discovered candidate IDs and display information. Neither file contains resolved keys. Write preferences by temp file plus atomic replacement **before** publishing a deliberate `/models` choice to the active selection; on write failure report failure and leave the old in-memory choice. Cache writes are atomic best-effort, with read failure treated as cache absence and reported without disabling commands. Do not rewrite preference when cache refresh removes a candidate. An operator can correct a deliberately saved but now rejected upstream by selecting another candidate with its `/models` button (refreshing first when the cache is empty) or edit the preference and restart; there is no typed selection command. The runtime's **only** contact with the old combined `models-config.toml` is an existence check: if present, emit one actionable operator notice naming its path and advising deliberate selection via `/models`; never read its content, convert it, or write it, and preserve its bytes for manual inspection. Alternative: keep combined authoritative document or migration bridge; rejected because disposable discovery must not be a durable selection authority and conversion is explicitly out of scope.

At startup, load preference and cached candidates separately. A saved syntactically valid selector is the active selection even when absent from cache. If no saved selection and cached candidates exist, take the first in stable canonical-ID lexicographic order **in memory only**. Only when both are absent, perform a one-time bootstrap discovery; select its first candidate in the same order, again without saving. Empty/all-failed discovery leaves `/models` and non-model commands available; implicit chat requests fail locally with an actionable missing-selection message; configured explicit targets still work. Invalid saved selector shape or unknown configured connection is reported actionably, not silently turned into an automatic selection; operator repairs/removes preference, or uses a valid explicit request. An unreadable or unparseable `model-selection.toml` likewise leaves selection unavailable: preserve its bytes without overwriting them, report the problem actionably without exposing content, and neither choose from cached candidates nor bootstrap an automatic selection while it is corrupt; commands and valid explicit requests remain available. The corrupt-bytes preservation rule binds automatic/runtime writes only: a deliberate candidate-button selection recovers immediately through the standing atomic replace, without a restart (with an empty cache the operator first refreshes until a provider returns candidates, or waits for providers to recover; no typed selection command or other hidden route exists); alternatively the operator repairs or removes the file and restarts. Refresh never changes the active selection. Alternative: random first model, unconditional startup network scan or select-and-persist first model; rejected for determinism, startup availability and deliberate preference semantics.

### 2. Direct, strict admission and pinned clients

The selector grammar is `connection-id/upstream-id`: split at **the first slash only**, require nonempty connection and nonempty upstream remainder (slashes within upstream remain intact); do not trim, alias, case-fold or consult cached model IDs. Check the connection ID against the fixed configured map, then resolve its credential and construct the existing immutable per-run client snapshot for that exact adapter/endpoint/upstream. Missing selector inherits active Main for ordinary implicit and scheduled jobs; an **explicit** ordinary/on-demand/plan/diagnostic/scheduled selector does not require Main selection. Missing Main on an implicit request, malformed shape and unknown connection fail locally with sanitized actionable errors. A syntactically valid upstream not discovered or not recognized by the provider is still sent; provider rejection is a normal failure, **never** fallback. Admission does not attest upstream callability. Respect per-run cancellation/closure, and preserve no-tool-replay, retry and checkpoint ownership. Selector errors for a **Scheduled run** affect that attempt/record/notification only, not the daemon or other jobs. Keep job `model` raw in the scheduler document; omission inherits active Main, while blank/non-string/unknown connection is an attempt failure (not a silent substitution). An explicit scheduled selector needs no Main. Alternative: retain catalog `admit()` and `admit_scheduled()` membership checks, Main gate, pre-admission fallback or model-switch guard; rejected because catalog is advisory and explicit jobs must be exact.

### 3. Independently configured auxiliary clients and fail-contained startup

`[embeddings]` explicitly specifies `provider` (adapter type), `base_url` (endpoint), `api_key` (credential source, e.g. `sec:...`), and `model`; `[graph_memory]` uses `extraction_provider`, `extraction_base_url`, `extraction_api_key`, `extraction_model` with the same four required values when graph is enabled. These are self-contained settings even when the adapter matches a chat connection: **no** chat connection endpoint, key, model, selection or catalog fallback; neither service inherits from the other. The existing embedding client serves indexing and graph vectors; graph extraction uses its independent LLM route, with per-extraction owned clients closed in `finally` on success, failure or cancellation. No fourth graph embedding section. Preserve graph's named fixed `max_tokens=1024`/`temperature=0.1` wire policy without a preflight fit gate. Graph startup and live backfill resolve their own settings directly with no Main, cache, preference or discovery prerequisite; dry-run still performs no inference/DB I/O.

Keep current graceful degradation: an absent/invalid embeddings setting makes indexing unavailable and graph unusable if it requires vectors; an invalid graph extraction setting disables **graph only** with a sanitized actionable warning; normal chat stays available. Validate required fields/credential references/adapter/endpoint before `GraphMemoryStore` construction (zero DB writes before valid configuration). Parse these independent subsystems into typed unavailable state rather than allowing a global `ConfigError` to abort startup merely because a disabled/optional subsystem is invalid. Invalid *chat connection* structural config still gets the existing startup error; this is not a generic swallow of config failures. Live backfill reports its own configuration failure before opening a DB. Retain existing graph drain/join ordering and bounded timeout/resource behavior. Alternative: register graph model as a third catalog entry or inherit a same-provider chat route; rejected for availability and credential isolation.

### 4. Counts-only context, one numerical compaction trigger, successful publication only

Replace `agent.ctx_max_tokens` and per-model context-window policy with `agent.compaction_threshold_tokens = 60000` (positive integer default; **estimated input tokens**, model-independent). Count system prompt, messages and current tool definitions with the existing estimator for threshold/diagnostics, preserving MAIN-only push snapshots and per-server tool-definition counts; show counts and threshold only, never capacity percentage, completion reserve, headroom or danger level. No model capability/capacity metadata influences a send or compaction decision. Keep a separate `agent.required_output_cap_tokens = 1024` (positive integer default): emit it only for adapters requiring an output parameter (currently Anthropic); ordinary adapters omit optional output caps, temperature and top_p. Do not size this cap to context or discovered limits; graph's fixed cap is separate. These are design defaults, **not** approvals claimed by the proposal: 60k is below the existing 90k local context default and close to the old 85%-minus-1024 heuristic (~75.6k), giving earlier summarization without pretending a universal provider limit; 1024 matches the old per-model default and graph fixed cap. Both are independently user-configurable; the numeric trigger is the only compaction policy knob. Alternative: derive model-specific limits/reserves, retain 256-floor or dynamically shrink cap; rejected as renewed budgeting.

Before each eligible send, if the estimate exceeds threshold, make **one** compaction attempt using the existing partition/span helpers (`_message_spans`, `_partition_compaction`) and the existing summary prompt. Preserve the active task/goal and the latest two messages expanded to **complete** native tool-call/result spans, unchanged; summarize only the eligible middle. If the middle is empty, do nothing (do **not** truncate short histories). Build a candidate on a copy, validate native group integrity and nonempty stripped summary, and publish `messages` plus updated `goal_idx` **only** after successful summary and validation. Do not cap goal, recent turns or summary head/tail; do not force-tighter loops, deterministic lossy fallback, short-context capping, recursive summary compaction, fit preview/guard or overflow-repair retry. The resulting context may still exceed the trigger; do not recur in the same step or require it to fit before send. After a successful compaction, later eligible sends may attempt again if still above threshold (unless an automatic failure has disabled attempts for this run), and an already-published summary is ordinary history that may enter a later eligible middle; "no recursive summary compaction" prohibits only same-step recursion on the just-published candidate. Preserve original history if summarization fails or returns empty. Automatic failure logs a sanitized warning, continues the original model request and disables further **automatic** attempts for that run only; cancellation propagates and is not recorded as a summarizer failure. Manual hidden `/compress` uses the same success-only rule, preserves history on failed/empty response and reports failure without disabling an unrelated run's automatic compaction. Summary calls use the same pinned client and existing summary retry/accounting ownership (distinct attempt state, not the main request checkpoint), but remove its preview budget gate. Leave protocol validation of actual wire payload, native argument/pairing validation and Ollama tool-schema payload integrity in place. Provider context rejection propagates through existing error/checkpoint path without an automatic overflow repair. Alternative: retain deterministic head/tail repair on failure; rejected because it silently destroys evidence and contradicts success-only replacement.

### 5. Scoped legacy removal, not a scheduler rewrite

Delete `migrate_models.py` including preview/`--apply`/`--recover`, its conversion/recovery tests and model-configuration compatibility code. Explicitly reject these obsolete configuration inputs with path plus replacement guidance rather than ignore/convert: top-level `[[models]]` (including `name`, `provider`, `model`, `api_key`, `base_url`, `request_timeout`, `max_tokens`, `temperature`, `top_p`, `vision`, `reasoning`, `aliases`, `context_window`, `max_retries`, `retry_delay`); `[agent] default_model`, `background_model`, `fallback_model`, `fallback_models`, `ctx_max_tokens`; `[providers.<id>]` model/generation/retry fields outside `type`, `api_key`, `base_url`, `request_timeout` (including `max_tokens`, `temperature`, `top_p`, `model`, `max_retries`, `retry_delay`, `retries`); legacy per-job `fallback_models` and legacy `schedule_type` (`daily`, `interval` plus `time`, `hours`, `minutes`) in `[jobs.<tag>]`. The old combined `models-config.toml` receives **only** Decision 1's existence check and single actionable notice, never content-level parsing/rejection; the state-home JSON-only job representation is `scheduler_jobs.json` (some ADR-0037 prose uses the pre-XDG source name instead). New jobs remain in `scheduler.toml` with existing `cron`/`once` representation and raw selectors; legacy job config is **not executed or rewritten**, and a detected JSON-only file or obsolete TOML job field yields an actionable notice/manual conversion guidance without discarding the file. Keep file-load bad-job containment, TOML raw-document preservation, collision checking, atomic mutation, reload latch, scheduled history, ownership and notifications. Reject obsolete fields at job validation/attempt as appropriate without making a bad job take down the scheduler; do not introduce a converter. `migrate.py` remains the **unrelated XDG storage-layout migration** even if it copies an inert historic `data/scheduled_jobs.json` source file; its copied artifact is not registered as a job. Historical log/execution readers, memory formats, PID process lock, `/stop` and access controls remain unchanged. Alternative: delete all migration code or rewrite scheduler persistence to drop unknown fields; rejected for scope and data safety.

### 6. Test plan and implementation sequence (not a tasks artifact)

Inventory every predecessor test before removal: **keep** provider real-adapter/`httpx.MockTransport` wire and tool-schema checks, native dispatch/group integrity, credential isolation/redaction, retries/checkpoints/leases/no replay, graph writer drain/closure, scheduler atomic reload/history/ownership and root startup harness. **Rewrite** catalog/admission/Telegram selector, graph/backfill admission, context monitoring/compaction, config/XDG and scheduled selector suites for the new contracts. **Retire only policy-specific** budget tickets, fit/reserve/repair, catalog authority/provenance, live replacement, migration conversion and JSON-only job compatibility assertions. **Move generic regressions first** from `tests/test_model_switch_budget_guard.py`, `tests/test_request_preparation.py`, `tests/test_p2_compaction.py`, `tests/test_p2_graph_memory_admission.py`, and scheduler legacy suites into owner-focused suites before removing budget/legacy files; retain the real-client mock-transport and composition-root proof rather than replacing them with only mocks. **Add** explicit uncached/upstream-with-slash without Main, cache-empty/all-provider-fail bootstrap, deliberate atomic preference write versus cache failure/refresh, independently invalid embeddings/extraction with zero DB writes, successful/empty/failing/cancelled compaction (the failing, empty and cancelled cases preserve the original history and permit no further automatic attempts within the run; a successful compaction may re-trigger at later eligible sends while still above threshold), native span preservation, scheduler explicit failure/no substitution plus atomic TOML persistence/history, and graph extraction closure/drain-timeout tests. Mock network/filesystem boundaries, not app-owned resolver or compaction code. Maintain secret redaction and endpoint/key non-leakage. No test-count goal, new skips or xfails.

Implementation order for a later explicitly authorized apply: first classify tests and move non-policy regressions; then test-first separate preference/cache and startup/selector admission; introduce independent auxiliary config and graph/backfill validation; simplify stats/compaction and mandatory wire cap; remove obsolete policy/legacy paths only after preserved coverage is green; finally update user docs/config examples and run the complete suite/static checks. This order is a dependency explanation, **not** a request to start implementation.

## Risks / Trade-offs

- [Cache loses models or provider discovery fails] -> preserve saved selection, permit explicit configured upstream without cache, keep commands available and report missing implicit selection clearly.
- [Corrupt preference while the cache is empty and providers keep failing] -> report the corrupt state with refresh-only guidance and never choose automatically; selection resumes after a refresh returns candidates, or after the operator repairs or removes the file and restarts.
- [Unknown upstream or oversized context is rejected remotely] -> surface provider failure through existing retry/checkpoint behavior; never claim cache callability or silently switch models/repair history.
- [Preference write succeeds but UI publication fails, or old combined file remains] -> atomic write before in-memory publication; next restart reloads deliberate preference; leave old file untouched with the startup notice and manual inspection, no hidden migration.
- [Malformed independent auxiliary config unexpectedly aborts daemon or creates DB] -> validate per subsystem before constructing graph store, degrade only affected service, preserve structural chat config errors.
- [Compaction summary is empty, cancellation occurs, or recent native group is malformed] -> never publish a partial candidate, propagate cancellation, report failure as appropriate, validate group boundaries; automatic failure disables only current run's future auto attempts.
- [Retiring legacy JSON jobs strands operator schedules] -> actionable startup/command notice with old file path and manual TOML instructions; never delete/rewrite historical bytes or silently run them.
- [Removing guard-focused tests hides unrelated retry/security regression] -> inventory and relocate general checks before deleting suites; retain real transport/root integration tests.

## Migration Plan

Planning publication is a separate, approved **docs-only** planning branch based on `main`, carrying only reviewed new-change planning and later scoped ADR records; commit and merge that exact planning state to `main`, then bring it back to the implementation branch **before** a separately authorized apply. The pending predecessor implementation at `a57ab26` stays the application baseline; its pending specs are not treated as canonical. Do not merge implementation to publish planning. For an approved implementation deployment: back up `config.toml`, `scheduler.toml`, old `models-config.toml` and legacy `scheduler_jobs.json` out of band; update `[providers.<id>]` connections and independent `[embeddings]`/`[graph_memory]` entries, replace removed agent fields with the two chosen numeric keys as desired, manually transcribe needed legacy jobs into TOML `cron`/`once`, restart to fix connections for the new process, then select deliberately with `/models` if a durable choice is wanted. Existing combined file and legacy JSON remain on disk, unused; no automatic migration or deletion. The process PID lock stays in force. Rollback means stop, restore the old binary and backed-up config/state together, restart; do not interpret the new separate preference/cache as an old combined catalog. The XDG layout migration utility is unaffected.
